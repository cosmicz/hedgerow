#+title: Hedgerow — isolated container lab
#+date: [2026-10-09 Fri]

Reproducible, isolated Pi-hole lab for developing and demonstrating Hedgerow
without touching a venue network, a production router or a radio.
Tracker: ~cyber26-mtm~ (design, evidence, contract). Owner of this directory
during the event: the lab lane; application code lives in ~src/~ and ~tests/~.

* What this is, and is not
This is a ~docker compose~ project on the Docker Desktop VM of the host, not
three virtual machines. Observations produced here are ~mode=live~ with
~scope=lab:rg-lab~. They are not ~physical-live~ and prove nothing about a
real home network, a Raspberry Pi or any router firmware.

All lab services sit on one ~internal: true~ network, ~10.77.0.0/24~. Inside
the lab there is no default route, no NAT and no DNS forwarding: connects to
~1.1.1.1:53~ and to the Docker host resolver fail with "Network is unreachable",
and ~example.com~ does not resolve. The only bridge between the host and the
lab is the ~console~ service, a ~socat~ forwarder bound to ~127.0.0.1:8053~
with IP forwarding disabled. Docker does not publish host ports for containers
that sit only on an internal network, which is why the forwarder exists.

| Service | Address | Image (pinned) | Role |
|---------+---------+----------------+------|
| pihole | 10.77.0.53 | pihole/pihole:2026.09.0 | Appliance DNS base, authoritative for lab names |
| gateway | 10.77.0.80 | busybox:1.37-musl | Home gateway stand-in; HTTP banner at endpoint.lab.test; no DNS listener (Pi-hole upstream fails closed) |
| client | 10.77.0.100 | alpine:3.22 | Owned client, registered in Pi-hole group ~rg-lab~ only |
| client2 | 10.77.0.101 | alpine:3.22 | Control client, unregistered (Default group) |
| console | 10.77.0.2 + mgmt | alpine/socat:1.8.1.3 | 127.0.0.1:8053 -> pihole:80, nothing else |
| clickhouse | 10.77.0.90 | clickhouse/clickhouse-server:26.9-alpine | Optional, profile ~sponsor~; lab-internal only |

Image identities are enforced, not just recorded: ~lab/images.lock~ maps each
tag to its linux/arm64 image ID (config digest), ~lab/bin/lab up~ and ~reset~
refuse to start unless every loaded image matches and every compose image is
locked, and ~lab/test/check-images.sh~ asserts the same. Do not start services with
raw ~docker compose~ commands; they bypass the gate. ~lab/bin/lab baseline~
records the IDs that actually ran. On this host the Docker VM has no egress (VPN
resolver); images were pulled host-side with ~crane pull --platform
linux/arm64~ and ~docker load~. ~docker pull~ and ~apk/apt~ builds do not work
here, so the lab uses only stock images and no Dockerfiles.

For a fresh arm64 lab, acquire the listed tags before starting. This downloads
public images but starts no services; the identity gate then verifies the
actual config digests against ~images.lock~. A changed remote tag must fail the
gate, not prompt a blind lock-file update:
#+begin_src sh
while read -r tag digest; do
  case "$tag" in ''|'#'*) continue;; esac
  docker pull --platform linux/arm64 "$tag" || exit 1
done < lab/images.lock
lab/test/check-images.sh
#+end_src
If the Docker VM cannot reach registries, use host-installed ~crane~ for each
listed tag: ~crane pull --platform linux/arm64 TAG private/image.tar~, then
~docker load -i private/image.tar~ and repeat the image gate. This is an
alternative acquisition path, not permission to change the pinned identities.

* Local DNS names
Lab-local answers override ~wikipedia.org~, ~update-check.cloudsyncapi.net~,
and the reserved name ~endpoint.lab.test~ (all 10.77.0.80). Negative controls:
~never.invalid~ and ~example.com~ must never resolve. "Flagged" is a synthetic
label for the demo scenario, not live malicious infrastructure.

* Commands
#+begin_src sh
lab/bin/lab init        # once: writes ignored lab/.env with a generated API password
lab/bin/lab up          # start, wait healthy, provision group + owned client
lab/bin/lab check       # isolation (16), smoke (10), deny round-trip (9) assertions
lab/bin/lab reset       # down -v, up, provision: the reproducible baseline
lab/bin/lab baseline    # JSON evidence into lab/.state/ (ignored)
eval "$(lab/bin/lab env)"   # exports for the application; see below
lab/bin/lab down        # stop, keep volumes
lab/bin/lab sponsor-up      # optional ClickHouse profile, through the same image gate
lab/bin/lab sponsor-down
#+end_src

Checks are plain POSIX sh and fail loudly without a lab (exit 1); the deny
round-trip starts from the wrong state (name resolves), applies a group-scoped
rule, asserts the owned client gets ~0.0.0.0~ while the control client and
~wikipedia.org~ are unaffected, deletes the rule and asserts restoration.

* Application contract
~lab/bin/lab env~ prints: ~RG_PIHOLE_API_BASE~ (http://127.0.0.1:8053/api),
~RG_PIHOLE_API_PASSWORD~ (privileged; keep in the executor, never log, never
hand to a model), ~RG_PIHOLE_GROUP~ / ~RG_PIHOLE_GROUP_ID~ (rg-lab, read the id
from env), ~RG_LAB_CLIENT~, ~RG_LAB_CONTROL_CLIENT~, ~RG_LAB_SCOPE~,
~RG_LAB_FLAGGED~, ~RG_LAB_BENIGN~.

Pi-hole v6 API (core v6.4.3, FTL v6.7.1; version-matched spec at
~/api/docs/specs/*.yaml~ on the instance): ~POST /api/auth {password}~ returns
~session.sid~; send ~X-FTL-SID~ on every call; ~DELETE /api/auth~ ends the
session. Deny rules: ~GET/POST /api/domains/deny/exact~ with ~{domain, comment,
groups:[id], enabled}~, ~DELETE /api/domains/deny/exact/{domain}~ (204). List
changes apply asynchronously: verify the DNS postcondition, do not trust the
2xx. ~/api/dns/blocking~ is a global toggle and is out of bounds. Plain HTTP
is acceptable only because the port is loopback-bound inside this lab.

* Limits
DNS deny rules do not end existing connections, clear client caches, stop
direct-IP access or cover clients that use another resolver. The lab shows
exactly one coverage mode: clients explicitly using the appliance resolver.
Pi-hole gravity (blocklist download) cannot run here; the lab seeds an empty
~gravity.db~ from the image's own schema template so startup is deterministic.
